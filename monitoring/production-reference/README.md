# Production HA reference (separate from the affordable manifests)

The handwritten profiles are a single-replica homelab stack, including the `production` target profile. That name selects production application namespaces; it does not make monitoring highly available.

For an actual production monitoring deployment use the maintained `prometheus-community/kube-prometheus-stack` Helm chart with these reviewed values **instead of** the handwritten Prometheus, Alertmanager and Grafana resources. It provides the operator, kube-state-metrics, node exporter, Kubernetes rules/dashboards, two independent Prometheus replicas and three Alertmanager peers, each with storage and hard pod anti-affinity. This requires at least three nodes and sufficient capacity. Pin a tested chart version in your deployment repository; do not install an unreviewed latest chart.

Supply `monitoring-integrations` through your secret manager (including `grafana_username`), import the Boutique dashboard and Loki datasource, and deploy the incident bridge separately. ServiceNow is optional. When enabled, the current production adapter profile uses two workers sharing a dedicated PostgreSQL queue with leasing and the reviewed ServiceNow scripted upsert resource/unique index. SQLite profiles remain single-worker. Do not increase SQLite bridge replicas. Use managed object storage for production Loki with appropriate tenant auth, encryption, lifecycle policies and backups; filesystem Loki here is for the homelab.

This reference has not been deployed or tested against a Kubernetes cluster. Before production use, pin/render the Helm chart, verify operator CRDs and secret paths, restrict network policies, enable SSO/TLS for operator access, and run node-loss and notification-delivery drills. Alertmanager mesh deduplicates notifications but is not a durable event bus; HA Prometheus replicas need shared replica-independent alert labels. An external dead-man receiver is needed to detect loss of the entire monitoring stack.
